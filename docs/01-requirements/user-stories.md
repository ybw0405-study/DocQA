# 需求分析与边界定义

## 1. 文档目的

本文定义「智能学习助手」本期交付的用户需求、验收标准、边界情况、明确不做项，以及 Java 控制面与 Python 数据面的职责划分。后续 UML、数据库、接口契约和编码都必须能追溯到本文的需求编号；如果实现与本文冲突，先修改本文并说明影响范围，不能默默偏离。

## 2. 用户角色与目标

| 角色 | 目标 | 主要场景 |
|---|---|---|
| 学生（主要用户） | 用更少时间从课件中找答案，并避免错过课程与作业 | 上传课件、基于文档提问、导入课表、创建截止提醒 |
| 系统管理员/审计员 | 确认 AI 调用可追溯、成本可控、数据未被滥用 | 按 traceId 查执行记录、检查预算与 PII 脱敏结果、启用 Kill Switch |

本期是单用户学习工具，不做组织、班级、教师端和多人协作。所有“学生”数据按 `userId` 隔离，管理员只查看脱敏后的运行治理数据，不默认拥有读取学生文档正文的业务权限。

## 4. 用户故事与验收标准

### US-01 身份认证与数据隔离（P0）

**用户故事：** 作为学生，我要安全登录，并且只能访问自己的文档、会话和提醒，避免学习资料泄露。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 正常登录 | 已注册且状态正常的账号 | 使用正确邮箱和密码登录 | 返回 HTTP 200、JWT 和 `traceId`；JWT 有效期 2 小时，`sub` 为 `userId`；服务端 P95 响应时间不超过 500ms |
| 未认证访问 | 请求没有 JWT 或 JWT 已过期 | 调用任意受保护的文档、问答或提醒接口 | 返回 HTTP 401，错误码 `USR-AUTH-001`，响应体符合 ProblemDetail 且包含 `traceId`，不泄露资源是否存在 |
| 越权访问 | 用户 A 已登录，且用户 B 存在一份文档 | 用户 A 用 B 的 `documentId` 查询或提问 | 返回 HTTP 404，错误码 `DOC-NOT_FOUND-001`；不得返回 403 并暴露“该文档存在” |
| 暴力尝试 | 同一账号或同一 IP 在 1 分钟内已失败 5 次 | 第 6 次使用错误密码登录 | 返回 HTTP 429，错误码 `USR-RATE_LIMIT-001`，并带 `Retry-After` |

### US-02 分片上传、MD5 秒传与并发去重（P0）

**用户故事：** 作为学生，我要用分片方式上传较大的课件，并在内容已存在时秒传，避免重复等待和重复存储。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 初始化上传 | 用户已登录，文件为允许类型、大小不超过 50MiB | 调用上传初始化接口并提供文件名、大小、MD5、Content-Type | 返回 HTTP 201、`uploadId` 和至少 1 个 5MiB 分片的预签名 URL；URL 有效期 15 分钟；浏览器不接触 MinIO 密钥 |
| 秒传命中 | 同一用户已有一份 MD5 相同且状态为 `INDEXED` 的文档 | 再次初始化上传 | 返回 HTTP 200、`instantUpload=true` 和既有 `documentId`；P95 不超过 300ms；不再创建文档、不再投递解析消息 |
| 并发重复上传 | 同一用户用同一 MD5 同时发起 10 个初始化请求 | 10 个请求在同一秒内到达 | 仅产生 1 条有效文档记录和 1 条解析任务；其余请求返回同一 `documentId`，不得出现 5xx 或重复计费 |
| 跨用户相同内容 | 用户 A 已上传某 MD5 文件，用户 B 上传完全相同的文件 | 用户 B 初始化上传 | 不得把 A 的 `documentId` 返回给 B；B 只能获得自己的上传会话或自己的秒传结果，MD5 去重作用域为 `userId` |
| 非法文件 | 文件超过 50MiB 或类型不在 PDF/PPTX/DOCX/TXT 白名单 | 调用初始化接口 | 分别返回 HTTP 413 或 415，错误码为 `DOC-VALIDATION-001/002`，不创建对象和数据库记录 |

### US-03 异步解析、状态追踪与失败重试（P0）

**用户故事：** 作为学生，我要看到文档从上传、解析到可问答的明确状态；失败时要知道原因并可控重试。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 完成上传 | 分片已全部上传且对象大小、MD5 校验通过 | 调用完成接口 | 同步返回 HTTP 202、`documentId` 和 `PARSING`，P95 不超过 500ms；响应不代表解析已完成；解析任务只在此后异步投递 |
| 解析成功 | 文档为可解析的 10MiB PDF | Python 完成切分和向量写入 | 60 秒内状态变为 `INDEXED`；`chunk` 元数据数量与向量写入数量一致，状态查询接口可返回分块数 |
| 瞬时失败 | 解析过程中发生可重试的对象存储或向量库超时 | 消费者处理失败 | 自动重试最多 3 次，采用指数退避；重试次数耗尽后进入 `DEAD`，不再自动投递，并记录可查询的错误码 |
| 加密 PDF | 用户上传带打开密码的 PDF | 解析器读取文件 | 状态进入 `FAILED`，`errorCode=DOC-VALIDATION-003`，标记不可重试，不进行 3 次无意义重试；用户在 10 秒内看到“需先解除密码保护”的可执行提示 |
| 向量已写、状态未更新 | 解析器已成功写入 PGVector，但 `document-service` 更新状态时失败或事件丢失 | 故障在 5 分钟后恢复 | 对账任务发现长期停留在 `PARSING` 的文档并重投解析；Python 幂等跳过已存在向量；最终状态变为 `INDEXED`，向量和分块数量不重复 |
| 非法状态跳转 | 文档处于 `UPLOADED` | 收到完成事件之外的伪造状态更新 | 拒绝更新并记录审计事件；状态只能按状态机允许的边迁移 |

### US-04 文档问答、引用与低置信度（P0）

**用户故事：** 作为学生，我要针对自己上传的文档提问，得到带引用来源的回答；证据不足时系统要明确说不知道，不能编造。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 正常问答 | 用户拥有至少一份 `INDEXED` 文档，问题与该文档相关 | 在会话中发起提问 | HTTP 200；P95 不超过 8 秒、P99 不超过 12 秒；回答至少含 1 条引用，引用含 `documentId`、`chunkIndex`、`score` 和不超过 200 字的原文片段 |
| 低置信度 | 检索结果最高重排序分数低于 0.55 | 发起提问 | 返回 `budgetStatus=LOW_CONFIDENCE`；回答明确说明现有资料不足，不得生成无引用结论；不得引用用户无权访问的文档 |
| 预算耗尽 | 本次请求 `tokenBudget=8000`、`maxToolCalls=3`、`maxRounds=3` | Agent 在第 2 轮已累计超过 8000 token，或工具调用将达到上限 | 在超限前停止；`budgetStatus=BUDGET_EXHAUSTED`；`tokenUsed<=8000`、`toolCallsMade<=3`、`roundsUsed<=3`；不得继续调用 LLM 或工具 |
| 缓存命中 | 同一用户、同一文档版本和同一上下文在 10 分钟内问过完全相同的问题 | 再次发起相同问题 | P95 不超过 1 秒；不调用 LLM；返回结果与首次一致且引用可追溯；仍写入一条 `agent_execution` 审计记录 |
| Python 超时 | Python 服务在 15 秒内未返回 | 用户发起提问 | Java 在 15.5 秒内返回 HTTP 504、错误码 `AGT-UPSTREAM-002`；上传、提醒、登录接口不受影响；连续 5 次超时后熔断 30 秒 |
| 无权限文档 | 问题请求中混入用户无权访问的 `documentId` | 发起提问 | 返回 HTTP 404，不进入 Python 检索；不得泄露文档标题或分块内容 |

### US-05 会话连续追问与上下文预算（P2）

**用户故事：** 作为学生，我要在同一个会话里连续追问，系统能利用最近上下文，但必须受 token 预算限制。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 连续追问 | 同一会话已有至少 1 轮问答 | 发送包含“它”“这个定理”等指代的问题 | 请求携带最近 6 条消息且上下文不超过 2000 token；模型能结合上一轮主题回答，引用仍指向用户拥有的文档 |
| 跨用户会话 | 用户 B 拿到了用户 A 的 `conversationId` | B 调用问答接口 | 返回 HTTP 404，错误码 `AGT-NOT_FOUND-001`；不写入任何消息 |
| 超长历史 | 会话已有 30 条消息 | 用户继续提问 | 按“最近消息优先”截断或摘要，最终发送给模型的上下文不超过 2000 token，不能因历史过长突破总预算 |
| 下游失败 | 用户消息已持久化，但 Python 调用失败 | 请求返回 504 | 用户消息保留；不写入伪造的助手回答；同一 `Idempotency-Key` 重试不会产生重复用户消息 |
| 并发提问 | 同一会话已有一个请求处于 `RUNNING` | 用户立即发起第二个问题 | 串行处理或返回 HTTP 409 `AGT-CONFLICT-001`；不能生成互相污染的上下文 |

### US-06 ICS 课表导入、时区与 EXDATE（P1）

**用户故事：** 作为学生，我要导入 ICS 课表，系统正确处理重复课程、时区与 EXDATE 调休/停课日期。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 每周课程 + EXDATE | ICS 含一个 `RRULE:FREQ=WEEKLY` 的课程事件，并有 1 个 EXDATE | 导入课表 | 该事件只生成 1 条提醒规则记录；被 EXDATE 排除的日期没有触发计划；排除日之后的下一周正常排课 |
| 时区 | 事件 `DTSTART;TZID=Asia/Shanghai:20260907T080000` | 导入并查询提醒 | 数据库存 UTC 时间，展示时按 `Asia/Shanghai` 还原为 08:00；`EXDATE` 与主事件使用同一时区基准匹配 |
| 重复导入 | 同一 `UID` 的 ICS 被再次上传 | 第二次导入 | 相同 `SEQUENCE` 幂等忽略，不新增第二套课程和提醒；更高 `SEQUENCE` 才更新；更低 `SEQUENCE` 拒绝覆盖，避免旧文件回滚新安排 |
| 大文件与格式错误 | ICS 不超过 2MiB；或文件第 37 行缺少 `END:VEVENT` | 导入 | 合法文件在 P95 5 秒内完成（500 个 VEVENT）；格式错误返回 HTTP 422，指出行号或事件 UID，整批回滚，不产生半套课表 |
| 非重复事件 | ICS 只有一个 `DTSTART`，没有 `RRULE` | 导入 | 按一次性提醒处理，仍只产生 1 条规则记录，不展开成多行 |

### US-07 作业截止提醒、自定义提醒与可靠触发（P0）

**用户故事：** 作为学生，我要创建作业截止提醒和自定义提醒，重复提醒必须由单条规则表达，到点可靠触发且不重复。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 创建截止提醒 | 用户已登录，提供标题、截止时间、提前 2 小时提醒、时区 | 调用创建提醒接口 | 返回 HTTP 201 和 `reminderId`；`nextTriggerAt` 正确等于截止时间减 2 小时；只创建 1 行记录 |
| 幂等重试 | 已用同一个 `Idempotency-Key` 创建成功 | 24 小时内重试同一请求 | 返回同一 `reminderId` 和 HTTP 200/201 中的稳定结果；不创建第二条提醒 |
| 每周重复 | 规则为 `FREQ=WEEKLY;BYDAY=MO;UNTIL=...`，时区为 `Asia/Shanghai` | 创建后连续计算 4 次触发时间 | 数据库中只有 1 行提醒规则；4 次时间均正确；不得为每次触发插入新行 |
| 到点触发 | 提醒的 `nextTriggerAt` 已到 | 调度器扫描到该提醒 | 60 秒内发出 1 次 `reminder.due` 领域事件；重复扫描不得产生重复逻辑触发；成功后推进 `nextTriggerAt` 到下一次 |
| 暂停/完成 | 提醒处于 `ACTIVE` 且有未来触发时间 | 用户暂停或完成提醒 | 不再产生未来事件；状态查询显示暂停/完成；恢复时重新计算下一次触发而不是补发历史所有触发 |
| 非法规则 | 提供非法 RRULE、过去 10 分钟的时间或不支持的时区 | 创建提醒 | 返回 HTTP 422，错误码 `REM-VALIDATION-*`；不落库、不投递 |

### US-08 AI 调用可追溯、预算刚性与 Kill Switch（P1）

**用户故事：** 作为管理员，我要能追溯每次 AI 调用的 trace、预算和审计事件，并能独立启停 AI 能力。

| 场景 | Given（给定） | When（执行） | Then（期望） |
|---|---|---|---|
| 执行记录完整 | 任意一次问答请求进入 `agent-gateway` | 请求结束（成功、超时或预算耗尽） | 100% 产生 `agent_execution`，包含 `traceId`、状态、`tokenUsed`、`toolCallsMade`、`roundsUsed`、`latencyMs`；按 `traceId` 在 3 秒内可查 |
| 预算不可突破 | 请求携带 `tokenBudget`、`maxToolCalls`、`maxRounds` | Python 执行 Agent 循环 | 任何一次模型或工具调用前都原子检查预算；超限立即停止；实测超出预算的次数为 0 |
| 审计可追溯 | 一次问答包含检索、LLM 和工具调用 | 请求成功或失败 | 审计事件记录 `traceId`、`userId`（允许的标识，不是正文）、事件类型、耗时、token、工具次数、脱敏后的摘要；不记录完整 Prompt、完整问题、API Key 或连接串 |
| 追加写 | 审计库已有事件 | 任何应用尝试 UPDATE/DELETE 审计行 | 数据库权限拒绝；应用层也不提供修改/删除接口；审计事件只允许 INSERT |
| PII 不进 LLM | 问题包含手机号、身份证号、邮箱 | 发起问答并检查 Java 日志、审计记录和 Python 发出的模型请求 | 原始 PII 不出现在日志或审计中；Python 在调用 LLM 前再次校验/脱敏；发现 Java 漏脱敏时记录高优先级告警，原文仍不得进入 LLM |
| Kill Switch | AI 功能正常运行 | 管理员切换为关闭状态 | 30 秒内新的问答请求返回 HTTP 503、错误码 `AGT-UPSTREAM-003`；已有请求按 deadline 收尾；登录、上传、提醒和审计查询不受影响；开关不依赖 LangGraph 循环内部 |

## 5. 三个最易被低估的边界情况

### 5.1 加密 PDF 上传

**为什么容易被低估：** 上传接口只能看到字节流，文件的 PDF 头看起来完全合法；许多 PDF 解析库在打开加密文件时才抛异常，而且异常类型容易被统一包装成“解析失败”，进入可重试队列。

**不处理的后果：**

1. 同一个文件被反复解析、反复失败，浪费 CPU、Embedding 额度和队列容量，最后才进入 `DEAD`。
2. 用户只看到“解析失败”，不知道需要解除密码，反复上传，形成支持成本和差评。
3. 如果错误分类丢失，监控会把用户输入问题误判为系统故障，误导告警和值班。

**本期处理：**

- Python 在读取页面内容前检测加密状态，将其归类为**永久失败** `DOC-VALIDATION-003`，不再重试。
- 文档状态进入 `FAILED`，状态接口返回可执行提示“请先解除密码保护后重新上传”。
- 审计记录失败类别，但不记录 PDF 密码、正文或用户文件路径中的敏感信息。
- 前端仅对非永久失败展示“重试”按钮；加密 PDF 只展示“重新上传”。

### 5.2 ICS 文件含 EXDATE 调休/停课日期

**为什么容易被低估：** 开发者常把 ICS 当作“每次课程一行”的静态列表，看到 RRULE 后直接展开未来 N 周，忽略 `EXDATE`、时区、`RECURRENCE-ID` 等 RFC 5545 语义。调休场景中，被取消的那一周恰恰是用户最需要系统正确安静的一周。

**不处理的后果：**

1. 节假日或停课日错误提醒，破坏信任；用户可能直接关闭所有提醒。
2. 若按“展开后的每次课程”插多行，后续修改课程时间或新增 EXDATE 需要批量修复，容易产生重复和幽灵提醒。
3. 时区处理错误会让 08:00 的课在 00:00 或 16:00 提醒，且难以通过 UI 解释。

**本期处理：**

- 一个 ICS VEVENT 序列只对应 1 条提醒规则，RRULE 与 EXDATE 共同保存在同一行，不把重复事件展开成多行。
- EXDATE 按与主事件相同的 TZID 解析并按 UTC 归一化后匹配；多个逗号分隔的 EXDATE 值逐项处理。
- 导入先在同一事务内解析全部事件，任一格式错误整批回滚；重复导入按 `UID + SEQUENCE` 幂等更新。
- 本期明确不支持 `RECURRENCE-ID` 单次改期的完整覆盖语义，见“本期不做”。

### 5.3 同一文档并发重复上传

**为什么容易被低估：** 重试、双击、多标签页和前端自动重试都可能在同一秒发出多个 MD5 相同的初始化请求。单看每个请求都合法，只有在并发窗口里才会暴露“先查后写”的竞态。

**不处理的后果：**

1. 产生两份文档、两套解析任务和两套向量，重复消耗 LLM/Embedding 预算。
2. 两个任务以不同顺序更新状态，可能出现文档长期 `PARSING`、`chunk` 重复或删除一半的中间态。
3. 如果秒传查询跨用户复用，可能把 A 的 `documentId` 返回给 B，直接造成越权与资料泄露。

**本期处理：**

- MD5 去重作用域固定为 `userId + md5`，禁止跨用户返回对方的文档标识。
- 初始化阶段使用 Redis 分布式锁保护“查重 + 建记录”临界区，数据库唯一约束兜底；锁和幂等键都必须有超时，不能无限等待。
- 完成接口按 `documentId + indexVersion` 幂等；重复完成只返回当前状态，不重复投递解析消息。
- 并发验收以“1 条文档 + 1 条解析任务 + 无 5xx”为通过标准。

## 6. 本期不做

| 不做项 | 原因 |
|---|---|
| 支付宝/微信账单实时直连 | 个人开发者无法申请到稳定的账单直连 API 权限，涉及支付合规、用户授权和敏感金融数据；本项目定位为学习助手，即使未来扩展消费分析，也只能先做手工导入或离线文件解析。 |
| 前端直连 Python 服务 | 会绕开 Java 统一鉴权、限流、预算、审计、PII 第一层脱敏和 trace 传播；同时把内部服务地址与调用凭证暴露给浏览器。所有前端请求必须经过 Java Gateway。 |
| 短信、邮件、企业微信/微信外部推送 | 需要额外服务商账号、模板审核与费用，且与本期“站内提醒看板”目标无关；本期提醒以站内看板和状态查询为准。 |
| 文档分享、公开链接、多人协作 | 需要额外的共享权限模型、撤销机制和向量检索隔离；本期所有数据按 `userId` 私有，不引入跨用户读权限。 |
| ICS `RECURRENCE-ID` 单次改期覆盖 | 本期明确支持 RRULE 与 EXDATE，但不实现单次调课覆盖；强行半实现会让调课场景比不支持更危险。该能力列入后续需求。 |
| 本地大模型训练/微调 | 需要 GPU、训练集与模型评估体系，偏离应用开发主线；本期使用受控的 LLM API，通过 Prompt、RAG 和预算治理保证效果与成本。 |
| 原生移动端 App 与离线模式 | 先用 Vue 响应式页面覆盖桌面与移动浏览器；离线同步、冲突合并和本地向量检索会显著扩大范围。 |
| 跨用户的文档去重与共享索引 | 秒传只在同一用户内生效；跨用户共享索引会引入权限、删除一致性和推理缓存串号风险，收益不足以抵消复杂度。 |

## 7. Java 侧必须做与 Python 侧可以做

### 7.1 Java 侧必须做

| 能力 | 必须落点 | 为什么不能下放给 Python |
|---|---|---|
| 身份认证与授权 | `user-service` 签发/校验 JWT；Gateway 做入口鉴权；所有资源查询带 `userId` 条件 | 身份与资源所有者是业务事实，Python 不拥有用户表，无法做可靠授权 |
| 文档所有权与状态机 | `document-service` 维护 `UPLOADED/PARSING/INDEXED/FAILED/DEAD`、重试次数、删除与访问控制 | 状态机是业务一致性核心，必须由拥有业务库的 Java 控制 |
| 业务持久化 | 用户、文档、会话、消息、提醒、审计的权威存储 | Python 不碰业务表；否则事务边界、数据修复和合规无法统一 |
| 上传编排与去重 | MinIO 预签名、分片、MD5 秒传、Redis 锁、RocketMQ 投递 | 秒传与并发去重涉及用户权限和业务唯一约束，不能由无状态 Python 决定 |
| 预算政策 | 生成 `tokenBudget/maxToolCalls/maxRounds`，写入审计，按用户/请求限流，核对最终用量 | 预算规则属于产品与计费政策，不能由执行方随意放宽 |
| 审计权威存储 | `audit-service` 追加写、权限隔离、按 traceId 查询 | 审计必须独立于 AI 执行进程，Python 崩溃不能带走证据 |
| PII 第一层脱敏 | 进 Python 前按手机号、身份证、邮箱规则脱敏；日志与审计禁止原文 | 在跨信任边界前完成第一层是控制面职责，减少 PII 离开 Java 的机会 |
| 跨语言治理 | 只有 `agent-gateway` 可调用 Python；负责超时、熔断、deadline、错误映射、trace 透传 | 统一治理入口才能保证预算、审计与可观测性不被绕过 |
| 提醒规则与调度 | `reminder-service` 解析 RRULE/EXDATE、计算下一次触发、投递 MQ | 提醒是业务状态，必须与用户权限和持久化规则一起管理 |

### 7.2 Python 侧可以做

| 能力 | Python 允许做的事 | 边界 |
|---|---|---|
| 文档解析与向量化 | 解析 PDF/PPTX/DOCX/TXT、切分、Embedding、写入 PGVector、发布解析完成事件 | 不写用户表、文档业务表、提醒表；分块元数据通过事件交给 Java 落库 |
| RAG 检索 | 按 Java 传入的 `documentIds` 过滤向量、召回、重排、拼接上下文 | 检索范围只能使用 Java 授权的文档 ID，不能自行扩大 |
| Agent 编排 | LangGraph 状态机、多轮工具调用、超时与预算中断 | 不定义预算政策、不放宽 Java 给出的上限 |
| LLM 与工具调用 | Prompt 构造、模型调用、工具白名单执行、引用生成 | 工具不能直接读写业务库；工具入参出参进入审计信号 |
| PII 第二层校验 | 进 LLM 前再次检测和脱敏，发现 Java 漏脱敏时记录告警 | 不得把原始 PII 送入模型；是否阻断整体请求按 2C 协议执行 |
| 预算硬停止 | 每次 LLM/工具调用前原子检查剩余 token、工具次数、轮次和 deadline | 只执行 Java 下发的规则，不能自行提高上限 |
| 治理信号回传 | 返回 `confidence`、`budgetStatus`、`tokenUsed`、`toolCallsMade`、`roundsUsed`、`auditEvents` | 信号不是最终审计；最终审计由 Java 权威落库 |
| 解析事件发布 | 发布 `document.parse.completed/failed` 等领域事件 | 事件必须可幂等消费，不能替代 Java 状态机做最终裁决 |

### 7.3 划分依据

1. **信任边界。** Java 持有一切身份和所有权判断，Python 只接收已授权的文档 ID 和脱敏后的问题；这样即使 Python 被攻破，也不能直接读取用户表或任意文档。
2. **数据所有权。** 业务一致性需要事务：文档状态、提醒、审计和会话元数据都在 Java 数据库中，由拥有该库的模块负责。Python 拥有 PGVector 的向量数据，但不能替 Java 决定业务状态。
3. **AI 迭代速度。** Prompt、检索策略、LangGraph 节点和模型选型变化快，放在 Python 可以独立发布；Java 只维护稳定的治理协议，不被模型实验拖慢。
4. **故障隔离。** Python 不可用时，登录、上传、提醒仍应工作；控制面不应把 LLM 依赖放进核心事务或启动链路。
5. **审计独立。** 预算与审计必须由不执行模型的 Java 侧掌握，才能在被执行方崩溃、绕路或失控时保留证据。
